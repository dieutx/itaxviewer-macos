# Original Mission Prompt

> This is the working brief for the project. Give this file together with `AGENTS.md` and
> `docs/MACOS_HANDOFF.md` to the agent working on the macOS machine.

You are a senior reverse engineer, macOS application architect, Swift developer, and XML/XSLT
interoperability specialist.

Your mission is to reverse engineer the official Vietnamese Tax Authority's Windows
application, **iTaxViewer**, using REA (Reverse Engineer Anything), then build a fully
functional, independent, native macOS application that reproduces its document-reading
behavior.

This is NOT a UI-only cloning task. The primary goal is functional compatibility with real
Vietnamese tax XML files generated by HTKK, eTax, and other official tax systems.

## TARGET APPLICATION

- Name: iTaxViewer (official Windows application)
- Application files: `C:\Program Files (x86)\iTax Viewer` (resolved during analysis)
- Target macOS: macOS 13+
- Architectures: Apple Silicon (arm64), Intel (x86_64)
- Preferred stack: Swift, SwiftUI, AppKit, XML/XSLT processing
- Working project: `./iTaxViewerMac/`
- Final output: working macOS .app and reproducible Xcode/Swift Package project

## IMPORTANT OPERATING RULES

- Actively use the installed REA tools. Do not merely describe how reverse engineering could
  be performed.
- Inspect actual application artifacts and collect evidence.
- Never invent recovered algorithms, schemas, mappings, or functions.
- Separate verified findings from hypotheses.
- Analyze and recreate interoperability behavior, not proprietary implementation code.
- Only reuse templates, fonts, images, and other assets when their licensing permits.
- Never bypass security, licensing or signature-verification mechanisms.
- Do not upload sensitive XML documents to remote services.
- Prefer working code and reproducible tests over lengthy planning documents.

## PHASE 1 — APPLICATION RECONNAISSANCE

1. Discover all files in the iTaxViewer distribution.
2. Identify executable files, DLLs, libraries, archives, resources, templates and
   configuration files.
3. Determine the implementation technology:
   - Native C/C++
   - .NET / WinForms / WPF
   - Java
   - Electron
   - Embedded browser
   - Or another framework

   Do not assume the original technology before inspecting the artifacts.
4. Identify executable entry points and important modules.
5. Examine file metadata, imports, strings, resources, configuration, and references using
   REA and the appropriate analysis provider.
6. Identify dependencies on Windows APIs and classify which features need native macOS
   replacements.
7. Locate any XML schemas, XSLT stylesheets, HTML templates, CSS, images and tax-form
   definitions.
8. Produce a technical architecture map of the original application.

Create:
- `docs/reverse-engineering/architecture.md`
- `docs/reverse-engineering/file-inventory.md`

Every significant finding should reference its source artifact, symbol, offset or other
reproducible evidence.

## PHASE 2 — RECOVER DOCUMENT PROCESSING

This is the highest-priority phase.

Investigate the complete workflow:

```
Open XML
→ Detect document type
→ Parse XML
→ Validate document
→ Select corresponding form/template
→ Map XML values
→ Render document
→ Print or export
```

Use REA to identify the functions and data responsible for each step.

Investigate:

### A. XML PARSING

- Supported XML structures and namespaces
- Encodings, including UTF-8 and UTF-16
- Handling of Vietnamese Unicode
- Error handling for malformed files
- Root element and metadata extraction
- Document-version identification
- Schema and namespace compatibility

### B. DOCUMENT CLASSIFICATION

Recover how the application distinguishes:

- VAT declarations
- Personal income tax declarations
- Corporate income tax declarations
- Financial statements
- Tax payment documents
- Tax authority notifications
- Appendices and supporting schedules
- Other supported official tax forms

Create a documented registry of confirmed document types, identifiers and their corresponding
rendering templates.

### C. TEMPLATE ENGINE

Determine whether iTaxViewer uses:

- XSLT transformations
- HTML/CSS rendering
- Embedded web components
- Native Windows drawing APIs
- PDF generation
- A custom template engine

Recover the actual rendering pipeline.

Identify:

- Template selection rules
- XML-to-field mappings
- Conditional sections
- Repeating tables
- Numeric formatting
- Date formatting
- Vietnamese text formatting
- Page breaks
- Print margins
- Header/footer behavior

Do not assume that every tax form uses the same schema.

### D. DIGITAL SIGNATURES

Investigate whether and how the original verifies XML digital signatures.

Distinguish:

- Signature presence
- Cryptographic signature validity
- Certificate chain trust
- Certificate validity period
- Revocation status
- Signing timestamp

If complete verification is not implemented, display "Not verified" rather than claiming the
document is valid.

### E. OUTPUT

Recover the observable behavior of:

- Open
- View
- Zoom
- Print
- Save/export
- Error messages
- Document navigation

Deliver:
- `docs/reverse-engineering/xml-pipeline.md`
- `docs/reverse-engineering/document-types.md`
- `docs/reverse-engineering/template-engine.md`
- `docs/reverse-engineering/signature-verification.md`

## PHASE 3 — BUILD A NATIVE MACOS APPLICATION

Implement the independent application using Swift and SwiftUI.

Use AppKit wherever SwiftUI does not provide sufficient desktop functionality.

Preferred architecture:

```
iTaxViewerMac/
  App/
  Features/
    FileBrowser/
    DocumentViewer/
    PrintExport/
    SignatureInspector/
  Core/
    XMLParser/
    DocumentClassifier/
    TemplateRegistry/
    TransformationEngine/
    SignatureVerification/
  Resources/
    Templates/
  Tests/
    Fixtures/
    Unit/
    Integration/
  docs/
```

The implementation must support:

1. Open XML files through native macOS file dialogs.
2. Drag and drop XML files into the window.
3. Open XML by double-clicking in Finder using file type registration.
4. Read multiple files and navigate between them.
5. Automatically detect supported tax document types.
6. Render documents with accurate Vietnamese tax-form layouts.
7. Display all mapped field values without changing source data.
8. Zoom in and out.
9. Print using native macOS printing.
10. Export rendered documents to PDF.
11. Display readable validation errors.
12. Show digital signature details where supported.
13. Support dark and light system appearances.
14. Run offline without a login, backend or cloud processing.

Use libxml2/libxslt or another suitable local XML/XSLT engine where justified by evidence.

A WKWebView-based local rendering component is acceptable when HTML/CSS provides better
compatibility with the original tax forms. The surrounding application must remain native
SwiftUI/AppKit.

### SECURITY REQUIREMENTS

- Parse documents locally.
- Disable external XML entities and unsafe DTD resolution.
- Block external network resources inside document previews.
- Prevent arbitrary script execution from imported XML.
- Handle large documents and malformed inputs safely.
- Do not log taxpayer information or full XML contents.
- Never transmit source documents without explicit user consent.

## PHASE 4 — USER INTERFACE

Create a professional native macOS document viewer.

Layout:

- LEFT SIDEBAR: recent files, open documents, document type, file name
- MAIN VIEW: rendered tax declaration, page navigation, zoom controls, scrollable preview
- TOP TOOLBAR: open, print, export PDF, zoom, document information, signature status

Use native macOS conventions, including:

- Cmd+O: Open
- Cmd+P: Print
- Cmd+S: Export
- Cmd+Plus: Zoom in
- Cmd+Minus: Zoom out

The UI should feel like a first-class macOS application while preserving the document
behavior of iTaxViewer.

Do not copy protected branding or present the app as an official Tax Authority product.

## PHASE 5 — COMPATIBILITY VALIDATION

Create a repeatable test suite using authorized or anonymized real tax XML samples.

Prioritize:

- 01/GTGT
- 05/KK-TNCN
- 05/QTT-TNCN
- 03/TNDN
- Financial statement XML
- Official tax notifications

For each supported document:

1. Open it with the original Windows iTaxViewer where a safe reference environment is
   available.
2. Record document classification and observable rendering behavior.
3. Open the same XML using the macOS implementation.
4. Compare all displayed data fields.
5. Compare table structures and conditional sections.
6. Compare document layout, pagination and PDF output.
7. Identify discrepancies.
8. Fix the root cause.
9. Add a regression test.

Do not use fake field values to conceal missing mappings.

For unavailable Windows runtime comparisons, explicitly mark validation as pending rather
than claiming compatibility.

Create a compatibility matrix:

- Document type
- Original version tested
- XML fixture
- Rendering support
- Data accuracy
- Print/PDF accuracy
- Signature support
- Test status

## PHASE 6 — BUILD AND PACKAGE

Generate:

- Complete source code
- Xcode project or Swift Package configuration
- Dependency documentation
- Unit and integration tests
- Reproducible build instructions
- macOS application bundle
- Optional DMG distribution package
- `README.md`
- `COMPATIBILITY.md`

Build and test for available architectures.

If code-signing or notarization credentials are unavailable, produce an unsigned development
build and document the exact signing/notarization steps. Do not pretend signing has succeeded.

## EXECUTION INSTRUCTIONS

Start immediately.

First:

1. Check REA connectivity and available analysis providers.
2. Inspect the actual target directory.
3. Determine the application technology.
4. Locate the XML processing and template resources.
5. Trace one representative XML-to-document rendering workflow.

Then begin implementing a minimal working macOS application that opens, identifies and
renders one verified tax XML type.

Expand compatibility iteratively.

Prioritize in this order:

- P0: Correct XML parsing and document classification
- P1: Accurate document rendering
- P2: Print and PDF export
- P3: Digital signature verification
- P4: Additional forms and UI improvements

Do not stop after generating an architecture document or UI mockup.

Write code, compile, run tests, inspect failures, fix defects and continue through the
implementation phases.

At each milestone report:

- Verified findings
- Source evidence
- Files created or modified
- Commands executed
- Tests passed/failed
- Remaining compatibility gaps

## FINAL SUCCESS CRITERIA

A real macOS user can double-click a supported Vietnamese tax XML file, have it open in the
native application, view the correct tax form with accurate values, print it, and export it
to PDF without using Windows.
